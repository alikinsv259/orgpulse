# OrgPulse

Дашборд для мониторинга орг-структуры компании: дивизионы → отделы → команды.
У каждого узла — численность, бюджет и метрика эффективности.

## Стек

| Слой | Технологии |
|------|------------|
| Клиент | React 19, Vite, TypeScript, React Query, styled-components, Zod, axios |
| Сервер | Koa 3, TypeScript, tsx |
| Контракт | `packages/api-contract` — типы маршрутов + Zod-схемы ответов |

## Запуск

### Docker (production-сборка)

```bash
docker compose up
```

Приложение на http://localhost:8080. Nginx отдаёт статику с gzip и проксирует `/api`
(включая WebSocket) на сервер, поэтому наружу торчит один порт.

Конфигурация — через `.env`, он не обязателен: без него берутся дефолты из кода.
Файл ищется в двух местах, и тот, что ближе к приложению, выигрывает:

1. `.env` в корне репозитория,
2. `apps/server/.env`.

Одинаково работает и в Docker (`env_file` в compose), и локально (`dotenv` в сервере).
Содержимое:

```
WEB_PORT=8080
CORS_ORIGIN=http://localhost:8080
LATENCY_MS=0
LIVE_INTERVAL_MS=3000
AI_SEARCH_MODEL=gpt-4o-mini
OPENAI_API_KEY=
```

Остановить: `docker compose down`.

### Локальная разработка

```bash
npm install
npm run dev
```

Одна команда поднимает оба процесса:

- API — http://localhost:4001
- Клиент — http://localhost:5173

## Переменные окружения

| Переменная | Где | По умолчанию | Назначение |
|------------|-----|--------------|------------|
| `PORT` | server | `4001` | Порт API |
| `CORS_ORIGIN` | server | `http://localhost:5173` | Разрешённый origin клиента |
| `LATENCY_MS` | server | `1000` | Искусственная задержка ответа, чтобы были видны состояния загрузки. `LATENCY_MS=0` отключает |
| `LIVE_INTERVAL_MS` | server | `3000` | Период рассылки live-патчей подключённым клиентам |
| `OPENAI_API_KEY` | server | пусто | Ключ OpenAI. Пустой — AI-поиск работает на локальном парсере |
| `AI_SEARCH_MODEL` | server | `gpt-4o-mini` | Модель для разбора поискового запроса |
| `WEB_PORT` | compose | `8080` | Внешний порт nginx |

Сервер читает `.env` через `dotenv` при старте, уже существующие переменные окружения
не перезаписываются. `.env` перечислен и в `.gitignore`, и в `.dockerignore` — в образ он
не попадает: контейнеру значения подкладывает `env_file` из compose.

`WEB_PORT` — исключение: это подстановка `${...}` в самом compose, а она читает только
корневой `.env`. В `apps/server/.env` эта переменная работать не будет.

`LATENCY_MS` по умолчанию равен `1000` в разработке (чтобы были видны состояния загрузки)
и `0` при `NODE_ENV=production`, который выставлен в образе. Отдельно задавать не нужно.

При старте сервер пишет, что именно подхватил:

```
[server] listening on http://localhost:4001
[server] .env: /app/.env
[server] ai search: openai (gpt-4o-mini)
```
| `VITE_API_URL` | web | `http://localhost:4001` | Базовый URL API |
| `VITE_LIVE_ORIGIN` | web | выводится из `VITE_API_URL` | Origin WebSocket-соединения (`http` → `ws`) |

## API

`GET /api/org-tree` — плоский массив узлов (42 узла, 3 уровня вложенности):

```json
{
  "id": "d1-p1-t1",
  "name": "Ядро",
  "parentId": "d1-p1",
  "headcount": 8,
  "budget": 8993000,
  "performance": 83,
  "updatedAt": "2026-09-14T14:00:14.180Z"
}
```

Ошибки отдаются единым конвертом:

```json
{ "error": { "code": "NOT_FOUND", "message": "Route GET /api/nope not found" } }
```

Данные детерминированы: сервер строит их из фиксированного сида, поэтому перезапуск
не меняет ответ — кэш на клиенте инвалидируется только при реальном изменении данных.

### WebSocket `ws://localhost:4001/api/live`

Пока подключён хотя бы один клиент, сервер раз в `LIVE_INTERVAL_MS` мутирует случайный узел
и рассылает патч. Без подключённых клиентов данные не меняются вообще.

```json
{
  "type": "orgNode.updated",
  "patch": { "id": "d1-p1-t1", "headcount": 9, "budget": 10117000, "performance": 79, "updatedAt": "2026-09-16T08:14:02.311Z" }
}
```

Патч — полная замена изменяемых полей узла, поэтому применение идемпотентно. Клиент валидирует
каждое событие через `LiveEventSchema` и молча отбрасывает то, что не прошло контракт.

### `GET /api/capabilities`

```json
{ "aiSearch": { "isLlmAvailable": false, "requiredEnvVar": "OPENAI_API_KEY", "model": null } }
```

### `POST /api/ai-search`

Тело — `{ "query", "stats" }`, ответ — `{ "filter", "summary", "confidence" }`.
Без ключа возвращает `503 AI_SEARCH_UNAVAILABLE`, и клиент переключается на локальный разбор.

```text
apps/

    src/config.ts    ENV
    src/errors.ts    AppError + errorHandler → { error: { code, message } }
    src/live.ts      WebSocket-сервер и рассылка патчей
    src/aiSearch.ts  разбор поискового запроса через OpenAI
    src/orgData.ts   детерминированный сид орг-структуры
    src/routes.ts    GET /api/org-tree
    src/index.ts     бутстрап
  web/               клиент, Feature-Sliced Design
    src/app/         провайдеры (React Query, ThemeProvider, GlobalStyle)
    src/views/       страницы (dashboard)
    src/widgets/     крупные блоки (orgTree, orgTable)
    src/entities/    доменные сущности + data-access хуки (orgNode)
    src/features/    пользовательские сценарии (orgSearch)
    src/shared/      apiClient, ApiError, liveClient, queryClient, тема, UI-примитивы
packages/
  api-contract/      @staff-pulse/api-contract — общий контракт
```

Правило импортов FSD: `shared → entities → widgets → views`, обратные импорты запрещены.

Относительных импортов в проекте нет — всё через алиасы:

| Алиас | Куда ведёт | Где настроен |
|-------|------------|--------------|
| `@/*` | `apps/web/src/*` | `apps/web/tsconfig.app.json`, `vite.config.ts` |
| `~/*` | `apps/server/src/*` | `apps/server/tsconfig.json` |
| `@contract/*` | `packages/api-contract/src/*` | tsconfig всех трёх пакетов + `vite.config.ts` |
| `@staff-pulse/api-contract` | публичный баррель контракта | npm workspace + `vite.config.ts` |

`@contract/*` нужен потому, что `@/*` уже занят вебом, а алиасы Vite глобальны на сборку:
внутри контракта `@/…` резолвился бы в `apps/web/src`. Прикладной код импортирует контракт
по имени пакета, `@contract/*` — только его собственные внутренние импорты.

## Ключевые решения

- **Контракт в отдельном пакете.** `RouteDef`-мапа маршрутов типизирует `apiClient.get`:
  URL и тип ответа связаны на уровне типов, руками ничего не дублируется.
  Пакет потребляется из исходников (`exports → ./src/index.ts`), без шага сборки.
- **Валидация только на клиенте.** Сервер оперирует типами, клиент прогоняет ответ через
  `GetOrgTreeResponseSchema`; несоответствие превращается в `ApiError` с кодом
  `INVALID_RESPONSE` и рисует состояние ошибки, а не падает на рендере.
- **Кэш — React Query.** `staleTime` 5 с даёт stale-while-revalidate: повторный заход
  берёт данные из кэша и обновляет их в фоне. Ретраи выключены для 4xx.
- **Отмена запросов.** `queryFn` прокидывает `signal` из React Query в axios, поэтому
  размонтирование компонента отменяет HTTP-запрос.
- **Ошибки как в проде.** Сервер отдаёт `{ error: { code, message } }`, интерсептор axios
  превращает это в `ApiError { code, message, status }`, тексты для пользователя
  определяются на клиенте по коду — бэкендовые сообщения в UI не протекают.
- **Никакого inline-CSS.** Вся стилизация — styled-components и одна тема.
- **Агрегация считается один раз.** `aggregateOrgTree` — один пост-ордер обход дерева,
  `Map<id, { totalHeadcount, totalBudget, averagePerformance }>`, мемоизируется в
  `useOrgTreeQuery` рядом с деревом. Фильтр и сортировка таблицы её не пересчитывают.
- **Состояние выделения поднято во view.** Дерево и таблица — контролируемые виджеты
  на пропсах; выбор строки в таблице разворачивает предков узла в дереве и подсвечивает его.
- **Live-патч применяется точечно.** `applyOrgNodePatch` пересчитывает агрегаты только для
  затронутого узла и его предков: путь наверх идёт по `parentId`, то есть O(глубины), а не O(n).
  Полный `aggregateOrgTree` запускается один раз на загрузку данных.

## Live-обновления

- Транспорт — WebSocket. Экспоненциальный backoff при обрыве: 1 с → 2 → 4 → … до 30 с,
  с джиттером 25 %. Успешное подключение сбрасывает счётчик попыток.
- Соединение открывается по первой подписке и закрывается, когда подписчиков не осталось —
  лишних сокетов нет. Статус в шапке: `Подключение…` / `Live` / `Переподключение…`.
- Патч применяется к локальному снапшоту без рефетча: React Query остаётся источником базового
  состояния, патчи живут отдельным слоем поверх него и схлопываются по `id`. Патч с `updatedAt`
  не новее текущего игнорируется, поэтому после фонового рефетча старые патчи становятся
  безопасными no-op.
- Обновлённые ячейки подсвечиваются и гаснут за 1.5 с. Анимация перезапускается через `key`
  на значении ячейки, без таймеров и лишнего состояния; на первой отрисовке не срабатывает.
- Раскрытие дерева анимируется переходом `grid-template-rows: 0fr → 1fr` — это анимация высоты
  контейнера, работающая во всех браузерах, в отличие от `height: 0 → auto`. Свёрнутые ветки
  остаются в DOM (иначе анимации не будет) и помечаются `inert`, поэтому не попадают ни в
  таб-порядок, ни в дерево доступности.
- `prefers-reduced-motion: reduce` отключает подсветку, пульсацию индикатора и анимацию раскрытия.
- Клавиатура в таблице: `↑`/`↓` — перемещение фокуса, `Home`/`End` — к первой/последней строке,
  `Enter` — выделить узел. Roving tabindex: в таб-порядке всегда ровно одна строка.

## Аналитическая таблица

- Раскладка: при ширине ≥1280px дерево и таблица показываются рядом (split-view),
  переключатель скрыт. Уже — табы «Дерево / Таблица».
- Столбцы: Подразделение, Уровень, Всего сотрудников, Бюджет суммарный, Средняя эффективность.
- Суммарные показатели включают сам узел и всех потомков; средняя эффективность взвешена
  по `headcount`: `Σ(headcount × performance) / Σ(headcount)`. При нулевой численности — 0.
- Таблица плоская, поэтому есть столбец «Уровень»; исходный порядок — обход дерева в глубину.
- Сортировка: клик по заголовку сортирует по возрастанию, повторный клик разворачивает
  направление (двойной клик = обратная сортировка).
- Фильтр по названию: ввод мгновенный, фильтрация с дебаунсом 250 мс.
- Клик по строке выделяет узел в дереве: предки автоматически разворачиваются, строка дерева
  скроллится в видимую область. На узком экране после клика происходит переход на вкладку «Дерево».
- Бюджеты в формате `12 345 678 руб.` (неразрывные пробелы, `Intl.NumberFormat('ru-RU')`).

## AI-поиск

Строка поиска над таблицей принимает естественный язык и превращает его в структурированный
фильтр — `{ text, levels, headcountMin/Max, budgetMin/Max, performanceMin/Max }` из контракта.
Фильтр применяется на клиенте; агрегаты при этом не пересчитываются.

Три уровня деградации, режим всегда виден под строкой поиска:

1. **OpenAI** — если на сервере задан `OPENAI_API_KEY` и запрос до модели вообще доходит.
   Короткие (меньше 10 символов) и однословные запросы к модели не отправляются: это почти
   всегда название подразделения, локальный поиск справится с ним точнее, мгновенно и бесплатно. `POST /api/ai-search` вызывает
   Chat Completions со structured output (`response_format: json_schema`, `strict: true`),
   поэтому схема фильтра гарантирована на уровне API. Под строкой поиска — короткое
   резюме того, что модель поняла.
2. **Локальный парсер** — незаметно для пользователя подхватывает запрос, если ключа нет,
   запрос упал или модель вернула пустой фильтр.
   Детерминированный разбор: уровни (`дивизионы` / `отделы` / `команды`), сравнения
   (`больше`/`от`/`выше` против `меньше`/`до`/`ниже`, плюс `>`/`<`/`>=`/`<=`), метрики
   (`эффективность`, `сотрудники`/`численность`, `бюджет`) и единицы (`тыс`/`млн`/`млрд`).
   Под строкой поиска два независимых чипа:

   - **доступность** — `ИИ-поиск · <модель>` с зелёной точкой либо `ИИ-поиск выключен`
     с подсказкой, какую переменную добавить в `.env`;
   - **что отработало на текущем запросе** — «разобрал ИИ», «разобрал парсер» или
     «поиск по названию». Появляется только когда запрос введён и разбор закончен.

   Разделение нужно потому, что один чип на оба смысла путал: на пустом запросе он показывал
   «Локальный парсер», и это читалось как «ЛЛМ-поиска здесь нет», хотя он был включён.
3. **Текстовый поиск** — если в запросе не нашлось ни одного структурного признака, весь
   запрос уходит в `filter.text` и работает как обычный поиск по названию.

### Расплывчатые и невнятные запросы

Вместе с запросом клиент передаёт распределение значений текущей таблицы — min / p25 / медиана /
p75 / max по каждой метрике, посчитанные по тем же агрегатам, в которых работает фильтр. Модель
опирается на него, а не на выдуманные пороги, и помечает результат полем `confidence`:

| `confidence` | когда | что видит пользователь |
|---|---|---|
| `exact` | в запросе есть числа, уровни или название | обычная подпись с тем, что понято |
| `guess` | пороги выведены из распределения | подпись с префиксом «Предположение:» |
| `unclear` | запрос вообще не про поиск подразделений | предупреждение, поиск падает на текстовый |

Неполное название — не повод для `unclear`: «инже», «перв», «ядр» трактуются как поиск по
названию с `confidence: exact`. Предупреждение показывается только если запасной текстовый
поиск тоже ничего не нашёл, иначе пользователь видит результаты и тревожное сообщение
одновременно.

Примеры на реальных данных (p25 headcount = 11, p75 budget ≈ 29.8 млн, p25/p75 performance = 58/80):

```
«мало сотрудников»                → guess   headcountMax=11              12 строк
«большой бюджет»                  → guess   budgetMin=29801000           11 строк
«средняя эффективность»           → guess   performanceMin=58 …Max=80    22 строки
«команды с эффективностью ниже 60»→ exact   levels=[3] performanceMax=60 10 строк
«ядро»                            → exact   text="ядро"                   1 строка
«Инже»                            → exact   text="инже"                   1 строка, без предупреждения
«хочу пиццу»                      → unclear text="хочу пиццу" (локально)  0 строк + предупреждение
```

Явное всегда важнее выведенного: если для метрики в запросе есть число, распределение к ней
не применяется. Первая версия промпта этого не оговаривала, и модель подменяла явные «ниже 60»
на p25 — поправлено правилом приоритета и примерами в промпте.

Ответ модели дополнительно нормализуется на клиенте (`normalizeOrgSearchFilter`): пустая строка
в `text`, пустой массив уровней и `levels: [1,2,3]` приводятся к `null` — такие «ограничения»
ничего не ограничивают, а без нормализации проверка «фильтр не пустой» перестаёт что-либо значить.

Сервер не валидирует ответ модели — он отдаёт её JSON как есть, а клиент прогоняет его через
`AiSearchResponseSchema`. Не прошло — молча уходим на локальный парсер. Это тот же принцип,
что и с `/api/org-tree`: бекенд типизирован, валидация живёт на клиенте.

Границы `\b` в парсере не используются: в JavaScript `\w` и `\b` не знают про кириллицу,
поэтому `отдел` нашёлся бы внутри слова, а предлог `от` — внутри `отдел`. Вместо них —
lookaround `(?<![а-яёa-z])` / `(?![а-яёa-z])`.
