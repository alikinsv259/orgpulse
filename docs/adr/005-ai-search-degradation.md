# 005. Трёхуровневая деградация AI-поиска

- Статус: принято
- Дата: 2026-09-16

## Контекст

Задание: «строка поиска принимает естественный язык; ответ — структурированный фильтр
на клиенте; fallback — текстовый поиск».

Практическое ограничение: у проверяющего может не быть ключа от языковой модели. Фича,
которая без ключа просто не работает, в тестовом задании бесполезна.

Дополнительное требование появилось по ходу: расплывчатые запросы вроде «мало сотрудников»
модель должна трактовать, а не отвергать, а на совсем непонятные — предупреждать.

## Решение

Три уровня, переключение автоматическое:

1. **OpenAI** — `POST /api/ai-search` с structured output (`response_format: json_schema`,
   `strict: true`). Вместе с запросом уходит распределение значений текущей таблицы
   (min / p25 / медиана / p75 / max по агрегатам), чтобы пороги для «мало» и «большой»
   выводились из данных, а не выдумывались.
2. **Локальный парсер** — детерминированный разбор уровней, сравнений, метрик и единиц.
   Работает без ключа и без сети.
3. **Текстовый поиск** — если структурных признаков не нашлось, весь запрос уходит в
   `filter.text`.

Модель возвращает `confidence`: `exact` (в запросе явные числа или название), `guess` (пороги
выведены из распределения) или `unclear` (запрос не про поиск подразделений). На `unclear`
клиент откатывается на локальный разбор и показывает предупреждение — но **только если
запасной поиск тоже ничего не нашёл**.

Отдельное правило экономии: запросы короче 10 символов или без пробела к модели не отправляются
вовсе. Это почти всегда название подразделения, локальный поиск справится точнее и мгновенно.

Ответ модели нормализуется на клиенте: `levels: [1,2,3]`, пустой массив и пустая строка в `text`
схлопываются в `null`.

## Альтернативы

- **Только LLM.** Без ключа фича мертва, у проверяющего ничего не работает.
- **Только локальный парсер.** Формально не AI-фича и не тянет расплывчатые формулировки:
  «мало сотрудников» разобрать без знания распределения нечем.
- **Считать статистику на сервере.** Потребовало бы продублировать там агрегацию по поддеревьям,
  которая по замыслу живёт на клиенте. Вместо этого клиент присылает распределение сам —
  ручка интерпретирует запрос в контексте того, что пользователь сейчас видит.

## Последствия

- Фича работает у любого проверяющего; с ключом — лучше. Состояние явно показано двумя чипами:
  доступность ИИ-поиска и то, что отработало на текущем запросе.
- Промпт — вероятностная штука, и полагаться на него как на единственную защиту нельзя.
  Отсюда детерминированные страховки: нормализация фильтра, гейт предупреждения по результату,
  отсечение коротких запросов. Каждая из них закрывает конкретный наблюдавшийся сбой модели.
- Ручка зависит от данных, присланных клиентом. Для однопользовательского демо это нормально;
  для многопользовательского продукта статистику считал бы сервер.
- Интерпретация кэшируется на 5 минут по тексту запроса. Распределение намеренно не входит
  в ключ кэша: оно меняется на каждом live-патче, а переспрашивать модель из-за сдвига порогов
  на пару процентов незачем.
- Выдача модели недетерминирована: один и тот же запрос может дать чуть разные фильтры между
  сессиями. Лечится `temperature: 0`, пока не выставлено — часть моделей этот параметр отклоняет,
  а `AI_SEARCH_MODEL` настраиваемый.
