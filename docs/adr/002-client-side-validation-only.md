# 002. Валидация только на клиенте, бэкенд оперирует типами

- Статус: принято
- Дата: 2026-09-16

## Контекст

Задание требует: «схема API-ответа валидируется на клиенте; невалидный ответ — ошибка».
Одновременно бэкенд просили держать максимально простым — пара файлов без модульности.

Возник вопрос, где проходит граница доверия. Zod есть в контракте, и соблазн прогонять через
него ещё и ответы сервера очевиден.

## Решение

Zod живёт только на клиенте. Сервер импортирует из контракта **исключительно типы**
(`import type`), рантайм-зависимости от Zod у него нет.

Проверяется на клиенте:

| Источник | Схема |
|---|---|
| `GET /api/org-tree` | `GetOrgTreeResponseSchema` |
| `GET /api/capabilities` | `GetCapabilitiesResponseSchema` |
| `POST /api/ai-search` | `AiSearchResponseSchema` |
| События WebSocket | `LiveEventSchema` |

Непрошедший ответ превращается в `ApiError` с кодом `INVALID_RESPONSE` и рисует состояние
ошибки. Невалидное событие WebSocket отбрасывается молча — рвать соединение из-за одного
битого кадра смысла нет.

Сервер валидирует руками ровно одно: форму тела `POST /api/ai-search`, десяток строк без Zod.

Отдельное следствие: **ответ языковой модели проходит ту же проверку, что и обычный HTTP-ответ.**
Сервер не разбирает и не чинит её JSON, а отдаёт как есть. LLM — не привилегированный источник.

## Альтернативы

- **Валидировать на обеих сторонах.** Честнее для публичного API, но для задания это лишний
  рантайм-вес на бэкенде при нулевом выигрыше: сервер — единственный источник данных, и врать
  сам себе ему незачем.
- **Валидировать ответ модели на сервере.** Потребовало бы Zod на бэкенде ради одной ручки.
  Клиент всё равно обязан проверять ответ — получилась бы двойная работа.

## Последствия

- Бэкенд остаётся тонким: контракт для него — чистая документация типов.
- Клиент устойчив к любому мусору из сети, включая вывод модели.
- Расхождение контракта и реального ответа сервера обнаружится в рантайме на клиенте, а не
  на этапе сборки бэкенда. Для проекта такого размера приемлемо.
