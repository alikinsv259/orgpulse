# 001. Контракт API в отдельном пакете, потребляемом из исходников

- Статус: принято
- Дата: 2026-09-16

## Контекст

Сервер и клиент живут в одном npm-workspace, но это два независимых приложения. Формат
`GET /api/org-tree`, событий WebSocket и поисковой ручки нужно описать один раз, иначе типы
разъедутся при первом же изменении поля.

Отдельный вопрос — как пакет потреблять. Публикация в реестр для тестового задания избыточна,
а сборка в `dist` требует watch-режима в разработке и лишнего шага в инструкции запуска.

## Решение

`packages/api-contract` — пакет с `RouteDef`-картой маршрутов, Zod-схемами и доменными типами.
Потребляется **из исходников**: `exports` указывает на `./src/index.ts`, шага сборки нет.
Резолвится алиасами в `vite.config.ts` и `paths` в tsconfig всех трёх пакетов.

Карта маршрутов связывает URL с типом ответа на уровне типов:

```ts
apiClient.get('/api/org-tree')  // Promise<OrgNode[]>, вывод из ApiGetRoutes
```

Внутренние импорты пакета идут через собственный алиас `@contract/*`, а не `@/*` — алиасы Vite
глобальны на сборку, и `@/…` внутри контракта отрезолвился бы в `apps/web/src`.

## Альтернативы

- **Дублировать типы в обоих приложениях.** Отпадает: расхождение — вопрос времени.
- **Сборка в `dist`, как у боевого `@treema-ai/types`.** Реалистичнее для прода, но добавляет
  watch-сборку в dev и шаг в README. Для задания цена выше пользы.
- **Генерация из OpenAPI-спеки.** Больше инфраструктуры, чем требует одна ручка.

## Последствия

- Изменение контракта мгновенно видно обоим приложениям, без пересборки.
- `tsc` сервера не может собрать проект в одиночку — контракт лежит вне его `rootDir`.
  Прод-сборка делается esbuild'ом, который стирает type-only импорты; в рантайме сервера
  контракта нет вообще.
- Алиас `@contract/*` приходится прописывать в трёх tsconfig и в конфиге Vite.
