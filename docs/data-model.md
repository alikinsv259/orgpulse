# Модель данных

## Узел орг-структуры

Контракт: `packages/api-contract/src/domain/orgNode.ts`.

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `string` | Идентификатор, непустой |
| `name` | `string` | Название подразделения |
| `parentId` | `string \| null` | Родитель; `null` — корень |
| `headcount` | `int ≥ 0` | Собственная численность узла, без потомков |
| `budget` | `number ≥ 0` | Собственный бюджет узла, в рублях |
| `performance` | `number 0..100` | Собственная эффективность узла |
| `updatedAt` | ISO-8601 | Момент последнего изменения |

`GET /api/org-tree` отдаёт **плоский массив** таких узлов — 42 штуки, три уровня вложенности.
Иерархия выражена только через `parentId`.

Важно: `headcount`, `budget` и `performance` — **собственные** значения узла. У дивизиона это
его управленческий состав, а не вся численность дивизиона. Всё суммарное считается на клиенте.

## Дерево

`buildOrgTree` превращает плоский массив в дерево за два прохода:

1. каждый узел копируется в `Map<id, OrgTreeNode>` с пустым `children`;
2. для каждого узла ищется родитель в этой же карте — нашёлся, узел уходит к нему в `children`,
   не нашёлся, становится корнем.

Затем `assignLevels` обходит корни и проставляет `level`: 1 — дивизион, 2 — отдел, 3 — команда.

Порядок детей = порядок в исходном массиве, сервер отдаёт их структурно осмысленно.

Два вырожденных случая разобраны намеренно:

- **Потерянный родитель.** `parentId` указывает на несуществующий узел — узел становится
  корнем, а не пропадает.
- **Цикл.** `a.parentId = b`, `b.parentId = a` — оба уходят в `children` друг друга, ни один
  не попадает в корни, и рекурсия до них просто не доходит. Данные теряются, но зависания нет,
  и это сознательный размен: дешёвая защита от бесконечного цикла вместо полноценного
  детектора циклов.

## Агрегация

`aggregateOrgTree` — один пост-ордер обход, `O(n)`, результат `Map<id, OrgNodeAggregate>`.

```ts
type OrgNodeAggregate = {
  totalHeadcount: number       // Σ headcount по узлу и всем потомкам
  totalBudget: number          // Σ budget по узлу и всем потомкам
  weightedPerformance: number  // Σ (headcount × performance)
  averagePerformance: number   // weightedPerformance / totalHeadcount
}
```

Формула средней эффективности:

```
averagePerformance = Σ(headcountᵢ × performanceᵢ) / Σ(headcountᵢ)
```

где `i` пробегает узел и всех его потомков. Это **взвешенное** среднее, а не арифметическое:
команда из 40 человек влияет на показатель отдела сильнее, чем команда из четырёх.

`weightedPerformance` хранится в агрегате, хотя в UI не показывается. Без него инкрементальный
пересчёт невозможен: из готового среднего и новой численности исходную сумму произведений
не восстановить.

Краевой случай: `totalHeadcount === 0` → `averagePerformance = 0`. Без этой ветки получился бы
`NaN`, который молча протёк бы в сортировку и форматирование.

Считается один раз на загрузку данных, мемоизируется в `useOrgTreeQuery`.

Тесты: `apps/web/src/entities/orgNode/lib/__tests__/aggregateOrgTree.test.ts`.

## Снапшот

`createOrgSnapshot(nodes)` собирает всё, что нужно интерфейсу, в один неизменяемый объект:

```ts
type OrgSnapshot = {
  tree: OrgTreeNode[]                    // корни
  flatNodes: OrgTreeNode[]               // обход в глубину — порядок строк таблицы
  nodesById: Map<string, OrgTreeNode>    // доступ за O(1)
  aggregates: OrgNodeAggregates          // Map<id, агрегат>
}
```

## Контракт WebSocket-патча

Адрес: `ws://<host>/api/live`. Контракт: `packages/api-contract/src/api/live.ts`.

```json
{
  "type": "orgNode.updated",
  "patch": {
    "id": "d1-p1-t1",
    "headcount": 9,
    "budget": 10117000,
    "performance": 79,
    "updatedAt": "2026-09-16T08:14:02.311Z"
  }
}
```

Схема патча выведена из схемы узла через `OrgNodeSchema.pick(...)` — поля не разъедутся при
изменении домена.

Свойства протокола:

- **Патч — полная замена изменяемых полей**, а не дельта. Применение идемпотентно, порядок
  доставки одного и того же патча роли не играет.
- **`updatedAt` — версия узла.** Патч не новее текущего значения отбрасывается. Это делает
  безопасным фоновый рефетч: накопленные патчи после него становятся пустышками сами.
- **Клиент валидирует каждое событие** через `LiveEventSchema` и молча игнорирует непрошедшее.
- **Сервер мутирует данные только при наличии подписчиков.** Нет подключённых клиентов —
  `GET /api/org-tree` остаётся детерминированным.

### Инкрементальное применение

`applyOrgNodePatch(snapshot, patch)` возвращает новый снапшот:

```
дельты:  Δheadcount = patch.headcount − current.headcount
         Δbudget    = patch.budget    − current.budget
         Δweighted  = patch.headcount × patch.performance
                    − current.headcount × current.performance

путь:    id узла → parentId → parentId → … до корня        O(глубины)

для каждого узла пути:
         totalHeadcount      += Δheadcount
         totalBudget         += Δbudget
         weightedPerformance += Δweighted
         averagePerformance   = weightedPerformance / totalHeadcount   (0 при нулевой численности)
```

Полный `aggregateOrgTree` при этом не запускается. Ветка дерева от узла до корня клонируется
(новые ссылки на объекты, чтобы React перерисовал путь), остальные узлы переиспользуются
по ссылке.

Проверено тестом: результат инкрементального пересчёта совпадает с полным пересчётом, и меняются
ровно записи узла и его предков.

## Модель фильтра поиска

Контракт: `packages/api-contract/src/api/aiSearch.ts`.

```ts
type OrgSearchFilter = {
  text: string | null            // подстрока названия, регистронезависимо
  levels: number[] | null        // 1 дивизион, 2 отдел, 3 команда
  headcountMin / headcountMax: number | null
  budgetMin / budgetMax: number | null
  performanceMin / performanceMax: number | null   // 0..100
}
```

Все ограничения соединяются через «И», `null` означает «не ограничиваем».

Числовые границы сравниваются с **агрегированными** величинами — теми же, что показывает
таблица, а не с собственными значениями узла.

`normalizeOrgSearchFilter` схлопывает к `null` то, что ничего не ограничивает: пустую строку
в `text`, пустой массив уровней и `levels: [1,2,3]`. Иначе проверка «фильтр не пустой» теряет
смысл, а модель такие значения периодически возвращает.
