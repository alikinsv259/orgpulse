# 004. WebSocket для live-обновлений вместо SSE и поллинга

- Статус: принято
- Дата: 2026-09-16

## Контекст

Задание допускает три варианта: WebSocket, SSE или эффективный поллинг «с учётом частоты
изменений, backoff и минимизации лишних запросов». Отдельно в списке того, что сдавать,
упомянут «контракт WebSocket-патча» — то есть ожидание вполне конкретное.

## Решение

WebSocket на `/api/live`, пакет `ws` на сервере, нативный `WebSocket` на клиенте.

Клиентский `liveClient` — обычный класс, не завязанный на React:

- соединение открывается по первой подписке и закрывается, когда подписчиков не осталось;
- экспоненциальный backoff при обрыве: 1 → 2 → 4 → … до 30 с, джиттер 25 %, счётчик попыток
  сбрасывается на успешном подключении;
- статус отдаётся в React через `useSyncExternalStore`.

Сервер рассылает патчи только при наличии подключённых клиентов. Никто не слушает — данные
не меняются, и `GET /api/org-tree` остаётся детерминированным.

## Альтернативы

- **SSE.** Ноль зависимостей на сервере, `EventSource` из коробки. Но встроенный реконнект
  не даёт управлять backoff'ом — пришлось бы закрывать соединение вручную и городить свой
  таймер, теряя главное преимущество. Плюс расходится с формулировкой про «контракт
  WebSocket-патча».
- **Поллинг.** Самый простой и самый расточительный: сервер мутирует данные редко и неравномерно,
  большинство запросов вернули бы то же самое.

## Последствия

- На сервер добавлена зависимость `ws`; nginx требует явного апгрейда для `/api/live`
  (`proxy_set_header Upgrade` / `Connection`) и увеличенных таймаутов.
- Транспорт двунаправленный, хотя сейчас используется в одну сторону. Запас на будущее есть,
  цена — чуть более сложный прокси-конфиг.
- Логика переподключения живёт вне React и покрывается обычным юнит-тестом, если понадобится.
