# Возможности интерфейса

## Аналитическая таблица

- Раскладка: при ширине ≥1280px дерево и таблица показываются рядом (split-view),
  переключатель скрыт. Уже — табы «Дерево / Таблица».
- Столбцы: Подразделение, Уровень, Всего сотрудников, Бюджет суммарный, Средняя эффективность.
- Суммарные показатели включают сам узел и всех потомков; средняя эффективность взвешена
  по `headcount`: `Σ(headcount × performance) / Σ(headcount)`. При нулевой численности — 0.
- Таблица плоская, поэтому есть столбец «Уровень»; исходный порядок — обход дерева в глубину.
- Сортировка: клик по заголовку сортирует по возрастанию, повторный клик разворачивает
  направление (двойной клик = обратная сортировка).
- Фильтр по названию: ввод мгновенный, фильтрация с дебаунсом 250 мс.
- Клик по строке выделяет узел в дереве: предки автоматически разворачиваются, строка дерева
  скроллится в видимую область. На узком экране после клика происходит переход на вкладку «Дерево».
- Бюджеты в формате `12 345 678 руб.` (неразрывные пробелы, `Intl.NumberFormat('ru-RU')`).

## Live-обновления

- Транспорт — WebSocket. Экспоненциальный backoff при обрыве: 1 с → 2 → 4 → … до 30 с,
  с джиттером 25 %. Успешное подключение сбрасывает счётчик попыток.
- Соединение открывается по первой подписке и закрывается, когда подписчиков не осталось —
  лишних сокетов нет. Статус в шапке: `Подключение…` / `Live` / `Переподключение…`.
- Патч применяется к локальному снапшоту без рефетча: React Query остаётся источником базового
  состояния, патчи живут отдельным слоем поверх него и схлопываются по `id`. Патч с `updatedAt`
  не новее текущего игнорируется, поэтому после фонового рефетча старые патчи становятся
  безопасными no-op.
- Обновлённые ячейки подсвечиваются и гаснут за 1.5 с. Анимация перезапускается через `key`
  на значении ячейки, без таймеров и лишнего состояния; на первой отрисовке не срабатывает.
- Раскрытие дерева анимируется переходом `grid-template-rows: 0fr → 1fr` — это анимация высоты
  контейнера, работающая во всех браузерах, в отличие от `height: 0 → auto`. Свёрнутые ветки
  остаются в DOM (иначе анимации не будет) и помечаются `inert`, поэтому не попадают ни в
  таб-порядок, ни в дерево доступности.
- `prefers-reduced-motion: reduce` отключает подсветку, пульсацию индикатора и анимацию раскрытия.
- Клавиатура в таблице: `↑`/`↓` — перемещение фокуса, `Home`/`End` — к первой/последней строке,
  `Enter` — выделить узел. Roving tabindex: в таб-порядке всегда ровно одна строка.

## AI-поиск

Строка поиска над таблицей принимает естественный язык и превращает его в структурированный
фильтр — `{ text, levels, headcountMin/Max, budgetMin/Max, performanceMin/Max }` из контракта.
Фильтр применяется на клиенте; агрегаты при этом не пересчитываются.

Три уровня деградации, режим всегда виден под строкой поиска:

1. **OpenAI** — если на сервере задан `OPENAI_API_KEY` и запрос до модели вообще доходит.
   Короткие (меньше 10 символов) и однословные запросы к модели не отправляются: это почти
   всегда название подразделения, локальный поиск справится с ним точнее, мгновенно и бесплатно. `POST /api/ai-search` вызывает
   Chat Completions со structured output (`response_format: json_schema`, `strict: true`),
   поэтому схема фильтра гарантирована на уровне API. Под строкой поиска — короткое
   резюме того, что модель поняла.
2. **Локальный парсер** — незаметно для пользователя подхватывает запрос, если ключа нет,
   запрос упал или модель вернула пустой фильтр.
   Детерминированный разбор: уровни (`дивизионы` / `отделы` / `команды`), сравнения
   (`больше`/`от`/`выше` против `меньше`/`до`/`ниже`, плюс `>`/`<`/`>=`/`<=`), метрики
   (`эффективность`, `сотрудники`/`численность`, `бюджет`) и единицы (`тыс`/`млн`/`млрд`).
   Под строкой поиска два независимых чипа:

   - **доступность** — `ИИ-поиск · <модель>` с зелёной точкой либо `ИИ-поиск выключен`
     с подсказкой, какую переменную добавить в `.env`;
   - **что отработало на текущем запросе** — «разобрал ИИ», «разобрал парсер» или
     «поиск по названию». Появляется только когда запрос введён и разбор закончен.

   Разделение нужно потому, что один чип на оба смысла путал: на пустом запросе он показывал
   «Локальный парсер», и это читалось как «ЛЛМ-поиска здесь нет», хотя он был включён.
3. **Текстовый поиск** — если в запросе не нашлось ни одного структурного признака, весь
   запрос уходит в `filter.text` и работает как обычный поиск по названию.

### Расплывчатые и невнятные запросы

Вместе с запросом клиент передаёт распределение значений текущей таблицы — min / p25 / медиана /
p75 / max по каждой метрике, посчитанные по тем же агрегатам, в которых работает фильтр. Модель
опирается на него, а не на выдуманные пороги, и помечает результат полем `confidence`:

| `confidence` | когда | что видит пользователь |
|---|---|---|
| `exact` | в запросе есть числа, уровни или название | обычная подпись с тем, что понято |
| `guess` | пороги выведены из распределения | подпись с префиксом «Предположение:» |
| `unclear` | запрос вообще не про поиск подразделений | предупреждение, поиск падает на текстовый |

Неполное название — не повод для `unclear`: «инже», «перв», «ядр» трактуются как поиск по
названию с `confidence: exact`. Предупреждение показывается только если запасной текстовый
поиск тоже ничего не нашёл, иначе пользователь видит результаты и тревожное сообщение
одновременно.

Примеры на реальных данных (p25 headcount = 11, p75 budget ≈ 29.8 млн, p25/p75 performance = 58/80):

```
«мало сотрудников»                → guess   headcountMax=11              12 строк
«большой бюджет»                  → guess   budgetMin=29801000           11 строк
«средняя эффективность»           → guess   performanceMin=58 …Max=80    22 строки
«команды с эффективностью ниже 60»→ exact   levels=[3] performanceMax=60 10 строк
«ядро»                            → exact   text="ядро"                   1 строка
«Инже»                            → exact   text="инже"                   1 строка, без предупреждения
«хочу пиццу»                      → unclear text="хочу пиццу" (локально)  0 строк + предупреждение
```

Явное всегда важнее выведенного: если для метрики в запросе есть число, распределение к ней
не применяется. Первая версия промпта этого не оговаривала, и модель подменяла явные «ниже 60»
на p25 — поправлено правилом приоритета и примерами в промпте.

Ответ модели дополнительно нормализуется на клиенте (`normalizeOrgSearchFilter`): пустая строка
в `text`, пустой массив уровней и `levels: [1,2,3]` приводятся к `null` — такие «ограничения»
ничего не ограничивают, а без нормализации проверка «фильтр не пустой» перестаёт что-либо значить.

Сервер не валидирует ответ модели — он отдаёт её JSON как есть, а клиент прогоняет его через
`AiSearchResponseSchema`. Не прошло — молча уходим на локальный парсер. Это тот же принцип,
что и с `/api/org-tree`: бекенд типизирован, валидация живёт на клиенте.

Границы `\b` в парсере не используются: в JavaScript `\w` и `\b` не знают про кириллицу,
поэтому `отдел` нашёлся бы внутри слова, а предлог `от` — внутри `отдел`. Вместо них —
lookaround `(?<![а-яёa-z])` / `(?![а-яёa-z])`.
